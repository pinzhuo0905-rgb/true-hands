# 架构设计

## 一句话

在「模型决策」和「执行动作」之间**插一道不可绕过的网关**，让模型只能走界面这条路。

## 分层

```
┌─────────────────────────────────────────────────────────────┐
│  tasks/          任务定义：目标 + 界面验收方式                │
├─────────────────────────────────────────────────────────────┤
│  harness/        决策循环：观察 → 决策 → 校验 → 执行 → 验收    │
│    ├── loop.py       调度主循环                              │
│    └── verifier.py   界面验收器                              │
├─────────────────────────────────────────────────────────────┤
│  policy/     ★   策略网关：白名单 / 黑名单 / 参数级校验        │
│    ├── rules.py      规则表（项目的「宪法」）                  │
│    └── guard.py      执行校验、记录违规                       │
├─────────────────────────────────────────────────────────────┤
│  driver/         执行层：把动作变成真实桌面操作                │
│    ├── base.py       Driver 协议                             │
│    ├── mcp_client.py 通过 MCP 协议驱动（可换任意桌面服务器）    │
│    └── mock.py       测试用假驱动                             │
├─────────────────────────────────────────────────────────────┤
│  model/          模型层：观察 + 任务 → 下一步动作              │
│  evidence/       证据层：截图、轨迹、报告                     │
└─────────────────────────────────────────────────────────────┘
```

## 数据流

```
Task
 │
 ▼
┌────────────────────────────────────────────────────────────┐
│ ① driver.observe()          截图 + 无障碍树                 │
│ ② guard.check_context()     焦点是不是落在终端里？            │
│ ③ model.decide()            输出 {"tool":..., "args":...}   │
│ ④ guard.check()         ★   白名单？黑名单？参数合法？        │
│      ├─ 拒绝 → 理由回灌给模型，回到 ①                        │
│      └─ 通过 ↓                                              │
│ ⑤ driver.act()              真的去点、去敲                    │
│ ⑥ evidence.record_step()    前后各截一张图，写入 trace.jsonl  │
└────────────────────────────────────────────────────────────┘
 │
 ▼
verifier.verify()   同样是界面操作：打开文件看一眼，而不是读磁盘
```

## 关键设计决策

### 1. 为什么用「默认拒绝」而不是「黑名单拦截」

黑名单永远列不全。模型的想象力比规则表丰富得多。所以：

> **只有显式列在白名单里的动作才被执行，其余一律拒绝。**

黑名单的作用不是拦截（白名单已经拦了），而是**给出清晰的拒绝理由**，让模型知道该怎么做才对。

### 2. 为什么策略网关要独立成层

如果约束写在驱动里，换一个驱动就失效了；如果写在循环里，测试很难覆盖。

独立成 `policy/` 层的好处：

- **可单测**：`tests/test_policy.py` 不需要任何真实桌面就能验证约束
- **可切换**：`mode="audit"` 只记录不拦截，用于做对比实验
- **可审计**：`guard.report()` 输出结构化报告，直接进证据链

### 3. 为什么拒绝理由要回灌给模型

否则模型会一直重试同一个动作，撞满步数上限。

回灌之后，模型能看到「你刚才想写文件，这不行，因为……」，从而改用界面路径。
连续 3 次不改则中止——**不能无限容忍偷懒**。

### 4. 为什么验收也必须走界面

如果验收靠读磁盘，那整个约束就破了一个洞：模型可以不用界面完成任务，
只要最后让验收环节确认文件存在就行。

所以 `Task.verify_prompt` 被强制要求写成界面操作：
「打开资源管理器 → 找到文件 → 双击打开 → 截图确认」。

**验收器拿不到任何读文件的工具**，所以「验收通过」本身也是界面操作的产物。

### 5. 参数级校验为什么必要

`App` 是合法动作（人也要双击图标才能开软件），但它可以启动 `cmd.exe`。

```
App({"name": "cmd.exe"})   ← 动作名合法，但等于开了一个 Shell 后门
```

所以 `Guard._check_executable()` 会检查要启动的目标，拦截所有 Shell 与解释器。

同理，`check_context()` 会在焦点落在终端窗口时发出警告——因为「往终端里打字」
等价于「执行命令」。

## 可替换点

| 想换什么 | 怎么做 |
|---|---|
| 桌面驱动 | 实现 `Driver` 协议，或用 `MCPDesktopDriver` 指向别的 MCP 服务器 |
| 模型 | 实现 `ModelProvider` 协议 |
| 验收方式 | 实现 `Verifier` 协议 |
| 约束规则 | 改 `policy/rules.py`（慎重） |
